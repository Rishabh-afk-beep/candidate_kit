# REVIEW.md

Here is my review of the starter code in `app/main.py`. I went through the helper functions, existing endpoints, and schemas line by line, testing edge cases and concurrency to catch where it broke.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 33-37) | It replaced hours/minutes directly on `punch_in` without accounting for IST timezone or overnight shifts. Worse, `int((punch_in - start).total_seconds() / 60)` threw away seconds before checking `> 10`, so 09:40:01 (10 min 1 sec) became `10`, failing `10 > 10` and incorrectly returning 0 late minutes. | Calling it with 09:40:01 on a 09:30 shift returned 0 instead of 10 minutes late. | Converted the punch time to IST, checked if it strictly passed `shift_start + 10 mins`, and calculated the floor of total elapsed minutes from shift start. |
| 2 | `compute_work_hours` (lines 40-41) | Used standard `round()`, which in Python does Banker's rounding (round half to even) instead of standard half-up rounding required by R4. | An interval of 18 seconds (0.005 hours) rounded down to 0.00 instead of 0.01; 90 seconds (0.025 hours) rounded to 0.02 instead of 0.03. | Switched to `Decimal(diff_seconds) / Decimal(3600)` with `quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`. |
| 3 | `compute_overtime` (lines 44-47) | Completely ignored the 30-minute threshold rule (R3) and broke on overnight shifts because it didn't shift the end time to the next calendar day. | Punching out 5 minutes after shift end returned 5 mins overtime instead of 0; overnight punch-outs gave negative overtime. | Added a check to only return minutes if >= 30, and added +1 day to the shift end boundary when `shift_end <= shift_start`. |
| 4 | `create_employee` (lines 79-80) | Checked for existing employee via `find_one()` right before `insert_one()`. Under concurrent duplicate requests, both pass the check and create duplicates. | Fired two simultaneous POST requests with the same `emp_code`; both returned 201 Created. | Added a unique index on `emp_code` at startup and caught PyMongo's `DuplicateKeyError` to return HTTP 409. |
| 5 | `create_employee` (line 82) | Used `datetime.now()` (naive local time) and stored/returned that object instead of BSON UTC and epoch milliseconds. | Stored timezone-naive records in MongoDB and returned strings instead of integer epoch milliseconds. | Used UTC `datetime.now(timezone.utc)` truncated to whole seconds, stored BSON UTC date, and returned integer milliseconds in the response. |
| 6 | `EmployeeIn` model (lines 53-61) | Missing contract validations: no regex for `emp_code` (`^EMP\d{4,6}$`), no validation that `shift_start != shift_end`, and no string length limits. | Creating an employee with code `123` or identical start and end shifts returned 201 instead of 422. | Added Pydantic field validators with patterns, lengths, and raised 422 if `shift_start == shift_end`. |
| 7 | `list_employees` (line 93) | Off-by-one pagination bug: calculated `skip = page * page_size`. On page 1, it skipped the first 20 records immediately! | Calling `GET /employees?page=1` returned items 21 to 40; the first 20 employees were invisible. | Changed to `skip = (page - 1) * page_size`. |
| 8 | `list_employees` (line 94) | Calculated `total = db.employees.count_documents({})` with an empty filter, ignoring whatever `department` was requested. | Filtering by `department=Engineering` gave the total count of the entire company, not the department. | Passed the actual query filter `q` into `count_documents(q)`. |
| 9 | `list_employees` (line 95) | Did not sort the results. Contract requires employees to be sorted by `emp_code` ascending. | Returned documents in arbitrary MongoDB storage order. | Added `.sort([("emp_code", 1)])` to the query. |
| 10 | `punch_in` (lines 101, 113) | Never checked if the employee actually exists before accessing `emp["shift_start"]`. | Punching in with a fake `emp_code` crashed the server with `TypeError: 'NoneType' object is not subscriptable` (500) instead of a clean 404. | Added a check: `if not emp: raise HTTPException(404, "Employee not found")`. |
| 11 | `punch_in` (lines 102, 108) | Converted `punched_at` using local server date, and ignored the overnight shift rule where punch-ins before `shift_end` belong to yesterday's shift. | Punching in at 05:00 IST for a 22:00-06:00 overnight shift was logged under today instead of yesterday. | Created `compute_attendance_date` to handle IST wall-clock conversion and overnight shift previous-day rollback. |
| 12 | `punch_in` (line 104) | Concurrency race condition: used `find_one` to check if a punch already existed for the day. | Two parallel punch-ins at the exact same millisecond both slipped through and created duplicate attendance documents. | Added a compound unique index on `(emp_code, date)` in MongoDB and caught `DuplicateKeyError` to return 409. |
| 13 | `punch_in` (line 65) | Accepted raw numbers, floats, strings, or seconds timestamps for `punched_at`. | Sending a 10-digit Unix timestamp (seconds) or a float passed through without error. | Added a strict validator ensuring `punched_at` is an integer between `100000000000` and `4102444800000`, rejecting anything else with 422. |
| 14 | `punch_in` (line 119) | Added `doc["id"] = str(res.inserted_id)`. The OpenAPI specification explicitly states attendance records have no ID fields. | Response payload had an unexpected `id` property. | Removed `id` from the output dictionary so it matches the `AttendanceRecord` schema. |
| 15 | `list_attendance` (lines 144-147) | Pulled the whole collection into memory with `list(...)` and sorted/sliced using Python list indexing. | Would run out of memory and hang with a realistic dataset of 100,000+ records. | Pushed sorting, skipping, and limiting directly into the MongoDB query cursor using indexes. |
| 16 | `list_attendance` (line 145) | Sorted only by `date` descending, omitting the required secondary sort by `emp_code` ascending. | Attendance logs on the same date had non-deterministic ordering. | Added compound sort `[("date", -1), ("emp_code", 1)]`. |
| 17 | `list_attendance` (lines 127-128) | Didn't validate date ordering when both `date_from` and `date_to` were provided. | Calling with `date_from=2026-07-10&date_to=2026-07-01` quietly returned an empty list with 200 OK instead of failing with 422. | Added a check raising 422 if `date_from > date_to`. |
| 18 | `health` (lines 72-74) | Dummy endpoint returning hardcoded `{"status": "ok"}` without checking MongoDB. | Calling `/health` returned 200 even if MongoDB was completely down or disconnected. | Changed it to execute `client.admin.command("ping")` and return 503 if the database is unreachable. |

---

### Things I looked at and decided were NOT defects

1. **Storing derived fields directly in MongoDB**: The starter stores `work_hours`, `late_minutes`, `overtime_minutes`, and `half_day`. At first glance, storing calculated values looks redundant, but `DATA_MODEL.md` explicitly states stored derived values are authoritative and analytics must read the stored numbers rather than recalculating them. Keeping them in the document is by design.
2. **Keeping dates and shift times as plain strings**: Dates like `joined_on` and `date` are `"YYYY-MM-DD"`, and shift times are `"HH:MM"`. While it might seem cleaner to use datetime objects, doing so forces artificial timezones onto pure calendar and wall-clock values. Leaving them as strings in both MongoDB and the API matches the specification.
3. **Putting all code into `app/main.py`**: A multi-file layout with routers and services would usually be cleaner, but the assignment instructions specifically instructed: *"Put all your code in this one file. It must start with uvicorn app.main:app --port 8000"*. Keeping everything in one file is intentional.
